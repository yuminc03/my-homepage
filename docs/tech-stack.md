# 기술 스택 결정
- 상태: **확정(2026-09-14)** — Astro + 일반 CSS + TypeScript + Markdown Content Collections. 요약은 `PROGRESS.md` 5-11
- 작성: 2026-09-14
- 비교 후보: Astro(추천안) · Next.js(React) · Vite + React SPA · 순수 HTML/CSS/JS

## 1. 이 사이트의 요구 사항 (판단 기준)
- **콘텐츠 중심**: 자기소개·프로젝트·스터디 글·세미나 기록. 글과 사진이 계속 쌓이는 구조가 핵심이다
- **읽기 전용·정적**: 로그인·댓글·실시간 데이터가 없다. 방문자가 보는 내용은 배포 시점에 모두 정해진다
- **사진이 많다**: 세미나 행사 사진, 프로젝트 스크린샷 → 이미지 최적화가 성능을 좌우한다
- **링크 공유**: 면접관·채용 담당자가 카카오톡·LinkedIn·메일로 링크를 받는다 → 링크 미리보기(OG 태그)와 검색 노출이 JS 실행 없이 동작해야 한다
- **동적인 부분은 작다**: 창 열기/닫기 전환, 상세 push, 테마 전환, Dock 자동 숨김, 스크롤 등장. 모두 CSS transition + 약간의 JS로 설계했다(`PROGRESS.md` 5-9)
- **혼자 유지보수**: 본업은 iOS 개발이라 웹 코드는 오래 방치돼도 다시 읽기 쉬워야 한다

## 3. 후보별 요약
### 3-1. Astro — 추천
- 요구 사항 1~4(콘텐츠·정적·사진·링크 공유)를 **기본 기능만으로** 충족한다. 설정으로 메워야 하는 부분이 가장 적다
- 동적인 부분은 island(필요 시 React도 가능) 또는 작은 `<script>`로 처리하고, 나머지는 JS 없이 HTML로 나간다
- 시안의 CSS(토큰 줄, `.site[data-theme]`)를 거의 그대로 옮길 수 있다

### 3-2. Next.js (React)
- 인터랙션 구현은 가장 편하고 채용 시장에서 가장 익숙한 이름이다
- 하지만 이 사이트에는 서버 기능(SSR·API·인증)이 필요 없어 **쓰지 않을 기능의 복잡도와 JS 비용**을 떠안는다. 정적 내보내기를 하면 `next/image` 같은 장점도 줄어든다

### 3-3. Vite + React SPA
- 창을 여닫는 "데스크톱 앱" 느낌을 만들기엔 자연스럽다
- 치명적인 약점은 **링크 미리보기와 검색 노출**. 포트폴리오는 링크로 공유되는 결과물이라 요구 사항 4와 정면으로 충돌한다. 첫 화면도 JS를 받아 실행한 뒤에야 보인다

### 3-4. 순수 HTML/CSS/JS
- 가장 가볍고 표준만 쓴다
- 하지만 메뉴바·Dock·테마 토큰을 모든 페이지에 복제해야 하고(지금 시안 파일이 겪는 문제와 같다), 글이 늘 때마다 목록 페이지를 손으로 고쳐야 한다. **"기록이 계속 쌓이는 사이트"라는 목적과 맞지 않는다**

## 4. Astro의 약점과 감수하는 이유
| 약점 | 이 사이트에서 감수할 수 있는 이유 |
| --- | --- |
| 페이지 이동이 문서 교체(MPA)라 창 전환처럼 "이어지는" 애니메이션이 SPA보다 까다롭다 | View Transitions API로 이전·다음 페이지 요소를 이어 붙일 수 있다. `ClientRouter`는 미지원 브라우저에서 대체 동작을 제공하고, 메뉴바·Dock은 `transition:persist`로 유지한다. 모션 설계가 이미 `transform`·`opacity` 기반이라 잘 맞는다 |
| island끼리 상태 공유가 불편하다(각자 독립된 작은 앱) | 공유할 상태가 테마 하나 정도다. `data-theme` 속성 + `localStorage`로 충분하고, 늘어나면 nanostores 같은 작은 스토어를 쓴다 |
| React보다 생태계·채용 시장이 작다 | 이 사이트의 목적은 웹 개발자 취업이 아니라 iOS 개발자로서의 기록이다. 필요한 부분은 React 컴포넌트를 island로 넣을 수 있어 막히지 않는다 |
| 콘텐츠를 고치면 다시 빌드·배포해야 한다 | 기록 사이트라 실시간 반영이 필요 없다. `git push` → 자동 배포로 몇 분이면 끝나고, git 기록이 곧 활동 기록이 된다 |
| 복잡한 앱형 UI(여러 창을 동시에 띄우고 드래그 등)로 커지면 한계가 온다 | 확정된 시안은 "한 번에 창 하나 + 상세 push"다. 그 이상이 필요해지면 해당 영역만 React island로 만들거나 그때 Next.js로 옮기는 것을 재검토한다 |

## 5. 세부 선택
### 5-1. 스타일링
| 기준 | 일반 CSS(스코프 스타일 + 전역 토큰 파일) | Tailwind CSS |
| --- | --- | --- |
| 시안 이식 | **시안의 CSS·custom property 토큰을 거의 그대로 옮긴다** | 클래스 이름으로 다시 번역해야 한다 |
| 테마 토큰 | `.site` / `[data-theme="light"]` 구조 그대로 | `@theme` + CSS 변수로 가능하지만 한 번 더 매핑 |
| 모션 토큰 | `--ease-*`·`--dur-*` 그대로 | 임의 값 클래스가 길어진다 |
| 읽기 쉬움 | CSS를 아는 사람이면 누구나 | 클래스 목록이 길어지고 Tailwind 규칙을 알아야 함 |
| 속도 | 새 스타일을 쓸 때 선택자·파일을 오가야 함 | 마크업 안에서 빠르게 작성 |
- 결정: **일반 CSS**. 처음 추천안은 Tailwind였지만, 시안이 이미 토큰 기반 CSS로 완성돼 있어 번역 비용만 생긴다. Astro 컴포넌트의 `<style>`은 자동으로 그 컴포넌트에만 적용되므로(스코프) Tailwind를 쓰는 주된 이유인 "스타일 충돌 방지"도 이미 해결된다

### 5-2. 그 밖의 구성
- 언어: **TypeScript**(Astro 기본). Content Collections 스키마가 글의 필드를 검사하고 타입을 만들어 준다
- 콘텐츠: `src/content/`의 Markdown(프로젝트·스터디·세미나 컬렉션 3개), 사진은 글 폴더 옆에 두고 `astro:assets`로 최적화
- 배포: **GitHub Pages 하위 경로** `https://yuminc03.github.io/my-homepage/`. 원격 저장소가 GitHub에 있어 GitHub Actions 자동 배포가 가장 간단하다. 하위 경로라 `base: '/my-homepage'`를 설정하고 내부 링크·에셋에 `import.meta.env.BASE_URL`을 붙인다
- 패키지 매니저: npm(추가 도구 설치 없이 시작). Node 24를 `.nvmrc`로 고정(Astro 7은 Node 22.12 이상 필요)
- 테마 토큰: CSS `light-dark(라이트, 다크)` + `color-scheme`. 시안의 다크 블록·라이트 블록 두 벌 대신 토큰 하나에 한 쌍을 둔다. 시스템 설정 기본값은 CSS만으로 적용되고, 사용자 선택은 `data-theme`이 `color-scheme`만 바꿔 고정한다

## 6. 예상 면접 질문과 답변 요지
### Q1. 왜 React나 Next.js가 아니라 Astro인가요?
- 사이트의 성격에서 출발했다. 읽기 전용 콘텐츠 사이트라 서버 기능이 필요 없고, 사진이 많고, 링크로 공유된다
- Next.js도 정적 사이트를 만들 수 있지만 React 런타임을 모든 페이지에 보내고, 정적 내보내기에서는 이미지 최적화 같은 강점이 줄어든다
- Astro는 기본이 JS 0KB이고 콘텐츠 검사·이미지 최적화가 내장이라, 같은 결과를 더 적은 코드와 비용으로 낸다
- 필요한 곳엔 React 컴포넌트도 island로 쓸 수 있어 선택지를 닫은 것은 아니다

### Q2. Island 구조의 한계는 무엇인가요?
- island는 서로 독립된 작은 앱이라 상태 공유가 어렵고, 페이지 전체가 하나의 상태로 움직이는 앱형 UI에는 맞지 않는다
- hydration 시점(`client:load`·`client:visible` 등)을 직접 정해야 해서, 잘못 고르면 인터랙션이 늦게 붙는다
- 이 사이트는 공유 상태가 테마 하나이고 창은 한 번에 하나라 한계에 닿지 않는다고 판단했다

### Q3. 페이지가 바뀌는데 창이 열리는 애니메이션은 어떻게 만들었나요?
- View Transitions API로 이전 페이지의 스냅숏과 새 페이지 사이를 브라우저가 보간한다. 같은 `view-transition-name`을 가진 요소끼리 위치·크기가 이어진다
- 메뉴바·Dock은 `transition:persist`로 DOM을 유지해 깜빡이지 않는다
- 미지원 브라우저는 애니메이션 없이 이동하고, `prefers-reduced-motion`이면 짧은 페이드로 줄인다(점진적 향상)

### Q4. 정적 사이트에서 다크 모드 깜빡임은 어떻게 막았나요?
- CSS가 그려지기 전에 `<head>`의 작은 인라인 스크립트가 `localStorage` → `prefers-color-scheme` 순서로 테마를 읽어 `data-theme`을 먼저 붙인다
- 색은 모두 CSS custom property라 속성 하나만 바뀌면 전체가 바뀐다
- 토큰은 `light-dark(라이트, 다크)` 한 쌍으로 정의했다. `color-scheme: light dark`이면 브라우저가 시스템 설정으로 한쪽을 고르므로, JS가 늦거나 꺼져 있어도 첫 방문은 시스템 테마로 그려진다. 사용자가 고른 값은 `data-theme`으로 `color-scheme`만 덮어쓴다
- 다크·라이트 두 블록을 따로 두는 방식과 비교하면 같은 토큰 이름을 두 번 관리하지 않아 한쪽만 고치는 실수가 사라진다. iOS Asset Catalog의 Color Set(Any/Dark 한 쌍)과 같은 구조다

### Q5. SSG·SSR·CSR의 차이와 이 사이트가 SSG인 이유는?
- SSG: 빌드 때 HTML 생성 → CDN에서 파일만 내려줌. SSR: 요청마다 서버가 HTML 생성. CSR: 브라우저가 JS로 생성
- 이 사이트의 내용은 배포 시점에 확정되고 사용자별로 다르지 않아, 서버 비용 없이 가장 빠른 SSG가 맞다

### Q6. 이미지가 많은데 성능은 어떻게 챙겼나요?
- 빌드 시 WebP/AVIF로 변환하고 여러 크기를 만들어 `srcset`으로 화면에 맞는 것만 받게 했다
- `width`·`height`를 지정해 레이아웃 흔들림(CLS)을 막고, 화면 밖 사진은 lazy 로딩한다

### Q7. iOS 개발자로서 웹 기술을 어떻게 이해했나요?
- Content Collections 스키마는 JSON을 `Codable`로 디코딩하며 필드를 검증하는 것과 같은 역할이다. 잘못된 글은 빌드 단계에서 실패한다
- Astro 컴포넌트는 SwiftUI `View`처럼 입력(props)을 받아 화면을 그리는 조각이고, 다른 점은 빌드 때 한 번 HTML로 굳는다는 것이다
- CSS custom property 토큰은 Asset Catalog의 Color Set(라이트/다크 값 한 쌍)과 같은 개념이다
